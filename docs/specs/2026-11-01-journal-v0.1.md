# Cooking journal, v0.1 (spec, 2026-11-01)

Status: accepted by Yehor on 2026-11-01 ("yes", W45). Parent designs: approvals shell spec
(`Egoushka/approvals` `docs/specs/2026-10-31-shell-design.md`, "recipes service S3", decision 1) and ADR 0005 stage K2b
(`Egoushka/switchknife` `docs/adr/0005-knowledge-kit.md`).

## Conclusion

A small .NET service that keeps **entries** of four kinds (recipe, technique, own creation, config), finds them by plain
text and by meaning, and plugs into the approvals shell through the integration manifest (approvals#23) and into any
agent through MCP. It is the second consumer of that manifest. The first entry is a config: the oven dial, marks 1-9.
No bot, no Android code, no new app.

## Why

Yehor started cooking seriously (2026-10-31). He re-asks the same questions ("what is mark 5 in degrees") and has no place
for his own variations. Recipe managers (Mealie, Tandoor) store recipes; whether they keep a cook log is UNKNOWN and was
not checked. A journal of his own entries, readable by an assistant, is the part nobody else will build.

**Value hypothesis (for Yehor, no money).** A saved entry is found again later and saves a question or a mistake.

**Cheapest test (starting values, calibrate after the window).** In 14 days from the first non-seed save:
- at least 10 entries saved (the seed does not count), and
- at least 2 lookups of an *older* entry (created at least 24 h before the lookup; 24 h because a re-read while cooking the
  same day is not recall).

Measured by the service itself: `journal_stats` (MCP) and `GET /stats`. **Stop condition:** fewer than 10 entries or fewer
than 2 older lookups after 14 days: add no features; find out why (capture too slow? search not trusted?) before more code.

## Scope

In: entries with versions; text search; meaning search; the oven-dial conversion; shell manifest, four screens and three
actions; MCP tools; lookup log and stats; a seeded oven-dial entry.

Out (each has a home elsewhere): import by URL and `Switchknife.SafeFetch` (R1 of the shell spec, next patch release);
photos, voice, cook log with ratings (shell spec S3 in full; until then cooks are entries of kind `creation`); pushing
recipes to `Switchknife.Knowledge` (K2b, once 50 entries exist); Native AOT (Decision 3).

## Entry

| Field | Rule |
|---|---|
| `id` | `e_` + 12 lowercase base32 characters, made by the service; the seed uses `e_oven-dial` |
| `kind` | `recipe`, `technique`, `creation` or `config` |
| `title` | 1-200 characters |
| `body` | Markdown, up to 20,000 characters |
| `tags` | up to 20, each 1-40 characters, lower-cased |
| `data` | optional JSON object up to 8 KB (a config's numbers live here) |
| `source` | optional `https` URL |
| `version` | starts at 1; every save adds one; old versions stay readable |

A save that names an existing `id` must carry the `version` it was based on; a mismatch is a conflict (409), so two
devices never overwrite each other silently.

**Dial config.** A `config` entry whose `data.type` is `"dial"` has `data.marks`: an object `{"1": 140, ..., "9": 240}` of
mark to °C. Marks are whole numbers, at least two, °C between 50 and 400, strictly increasing with the mark; otherwise the
save is refused with a field error. `dial_convert` turns °C into a position by linear interpolation between the two
nearest marks (175 °C on marks 3 = 170 and 4 = 180 is 3.5, set 4, half up); outside the marked range it answers an error
and does not extrapolate. `data.measured` says whether the numbers came from a thermometer.

## Search

- `text`: SQLite FTS5, ranked by bm25, over title, body and tags.
- `meaning`: embeddings from an OpenAI-compatible `/v1/embeddings` endpoint (`Embeddings:Url`), cosine over stored vectors
  (brute force; a personal journal is hundreds of entries, and 10,000 vectors of 1,024 floats is 40 MB).
- `hybrid` (default): reciprocal rank fusion of both with k = 60 (the constant from the original RRF paper).
- No embedding endpoint configured, or it fails: `hybrid` answers the text result and says `mode_used: "text"`;
  `meaning` answers 503. Search never pretends.

Retrieval quality is **not** claimed here. The gate is ADR 0005 K2b: recall@5 on a 20-question kitchen gold set, at least
the `rg` baseline + 0.15, once 50 entries exist (`journal_stats` shows the count).

## Shell integration (approvals#23 manifest)

`GET /shell/manifest` serves `shell-manifest/1`: id `recipes`, screens `home` (home), `entry` (`entry_id`), `entry-new`
(optional `entry_id`, to edit) and `oven`; actions `entry.save` (`offline.queue: true`), `entry.search` and `dial.convert`
(both online only); `mcp.url`. Screens are A2UI v0.9 documents (`createSurface`, `updateDataModel`, `updateComponents`)
with an `etag` and `ttl_s` 300 (a starting value). They follow the shapes in the approvals contract fixtures
(`contract/shell/consumers/recipes/*.json`) but are **not yet validated against the approvals schema**
(`contract/shell/check-shell.mjs`); do that before the shell relies on them. The approvals repo's own
`manifests/recipes.json` uses other names (recipe, cook-new, cook.save, ...); the two need aligning on the approvals side.
`POST /shell/actions/{name}` verifies the
signature `HMAC-SHA256(key, action_id|name|screen|at|h)`, refuses an `at` more than 10 minutes from the server clock (403),
and stores the first answer under `action_id`: a repeat gets the same body and `Idempotent-Replay: true`.
Every `/shell/*` and `/mcp` request needs `Authorization: Bearer <token>` and no `Origin` header (`Switchknife.McpGuard`).

## MCP tools

| Tool | Read-only | What |
|---|---|---|
| `entry_search` | yes | query, optional kind, mode, limit (default 10, max 50) |
| `entry_get` | yes | one entry with its version list; **records a lookup** |
| `entry_save` | no | create, or add a version; same code path as the `entry.save` action |
| `dial_convert` | yes | `celsius` to position, using the newest dial config or a named one |
| `journal_stats` | yes | counts, window, pass/fail of the cheapest test |

## Decisions

1. **Own repo `Egoushka/recipes`.** Map checked 2026-11-01: no recipes project exists; shell spec decision 1 says a new
   small .NET repo. Public, MIT. No personal data: the seed is the generic gas-mark scale (1 = 140 °C ... 9 = 240 °C),
   flagged `measured: false`, no oven model. Yehor replaces it with measured numbers.
2. **SQLite, one file.** One user, hundreds of rows, FTS5 built in, backup is a file copy. Postgres with pgvector is the move
   if the journal ever serves more than one person. Stop: if meaning search over the real journal exceeds 100 ms p95
   (starting value: the point where a screen stops feeling instant), put vectors in an index.
3. **Not Native AOT in v0.1.** The MCP SDK registers tools by reflection, and AOT status of the SDK is UNKNOWN. Try
   `dotnet publish -p:PublishAot=true` once after v0.1 and record the result here; do not block on it.
4. **ADR 0005 stages, not the Project 8 Roadmap view.** The W45 question "recipes and roadmap" was ambiguous. Assumption:
   the roadmap is the ADR's stage table, and this service is K2b's data source. Yehor corrects it if he meant the view.
5. **Entries, not the shell spec's full domain** (recipes with cooks and equipment profiles). A smaller model that already
   holds the oven dial and his own variations; the full domain is added when the 14-day test passes.
